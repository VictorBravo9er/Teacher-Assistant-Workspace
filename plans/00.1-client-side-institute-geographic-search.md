# Plan 0.1: Client-Side Institute & Cascading Geographic Search

> **Status**: ✅ **COMPLETED** (Verified with `npm run build` and `uv run poe lint`)

## 1. Problem Statement & Context
Currently, [`CreateClassModal.tsx`](file:///home/victor/antigravity/Teacher-Assistant-Workspace/frontend/src/features/classroom/CreateClassModal.tsx) uses 5 separate PostgreSQL RPCs (`search_institutes`, `search_districts`, `search_cities`, `search_states`, `search_countries`) to power autocomplete inputs on every keystroke.

This architecture has three major weaknesses:
1. **Network Latency & Keystroke Delay**: Every input field requires a 300ms debounce and a database round-trip, creating sluggish UI responsiveness.
2. **The "Chicken-and-Egg" Discovery Problem**:
   - `search_cities`, `search_districts`, and `search_states` query `public.institutes` to discover locations (`SELECT city FROM public.institutes GROUP BY city...`).
   - If no school in "Pune" or "Austin" has been created yet, searching for "Pune" returns zero results.
3. **No Geographical Validation or Cascading**:
   - The fields are completely disconnected: a user can select State = "Karnataka" and District = "Mumbai" with zero cross-validation.
   - Variations in casing and typos (e.g. `"bangalore"`, `"Bangalore "`, `"BANGALORE"`) create duplicate, fragmented location records.

## 2. Architecture & Design: Cascading Client-Side Model

```
                      [Institute Selection / Creation]
                                     │
           ┌─────────────────────────┴─────────────────────────┐
           ▼                                                   ▼
1. "Select Existing" Institute                     2. "Add New" Institute
   - Client-side cache of institutes                  - Cascading Hierarchy:
   - Instant in-memory fuzzy search                     Country (Static)
     (Name, City, State)                                  │
   - Zero debounce, zero network                          ▼
     calls on keystrokes                                State (Cascades from Country)
                                                          │
                                                          ▼
                                                        District (Cascades from State)
                                                          │
                                                          ▼
                                                        City (Smart Combobox + Free-text)
```

---

## 3. The Strategy for Geographic Fields (District & City)

### A. District: Cascading Administrative Dictionary
In educational systems (e.g. India), districts are strictly defined administrative divisions:
- There are exactly **780 districts** across 28 States and 8 Union Territories.
- A lightweight static JSON mapping (`Record<State, District[]>`) is only **~18 KB**.
- **Behavior**:
  - Selecting State (e.g. `"Maharashtra"`) immediately populates District with its 36 legitimate districts (e.g. `"Pune"`, `"Thane"`, `"Nagpur"`, `"Mumbai Suburban"`).
  - Eliminates typos, prevents cross-state mismatches, and works offline instantly.

### B. City: Smart Combobox (Suggestions + Free-Text Fallback)
Unlike districts, cities, towns, and university campuses are virtually unbounded:
- **Behavior**:
  1. **Curated Suggestions**: When a user selects a District, the City input suggests known towns/cities in that district and any cities already present in the cached institutes list.
  2. **Free-Text Entry**: If a campus is located in a rural village, new tech park, or suburb, the user can type any custom city name freely without being blocked.
  3. **Auto-Sanitization**: Automatically trims whitespace and formats input to Title Case (e.g., converting `"new delhi "` to `"New Delhi"`) before saving to PostgreSQL.

### Step 4.2: Client-Side Institute Cache & Service ([`frontend/src/services/instituteService.ts`](file:///home/victor/antigravity/Teacher-Assistant-Workspace/frontend/src/services/instituteService.ts))
Create a dedicated `instituteService` with TTL caching:
```typescript
import { supabase } from '@/lib/supabase';
import { secureStorage } from '@/lib/storage';

export interface InstituteSummary {
  id: string;
  name: string;
  type: string | null;
  district: string | null;
  city: string | null;
  state: string | null;
  country: string | null;
}

const CACHE_KEY_INSTITUTES = 'edu_institutes_directory';

export const instituteService = {
  async fetchInstitutes(forceRefresh = false): Promise<InstituteSummary[]> {
    if (!forceRefresh) {
      const cached = secureStorage.getCachedItemWithTTL<InstituteSummary[]>(CACHE_KEY_INSTITUTES);
      if (cached) return cached;
    }

    const { data, error } = await supabase
      .from('institutes')
      .select('id, name, type, district, city, state, country')
      .order('name');

    if (error) throw error;
    
    secureStorage.setCachedItemWithTTL(CACHE_KEY_INSTITUTES, data || [], 60 * 60 * 1000); // 1 hr TTL
    return data || [];
  },

  async createInstitute(payload: Partial<InstituteSummary>): Promise<InstituteSummary> {
    const { data, error } = await supabase
      .from('institutes')
      .insert({
        name: payload.name?.trim(),
        type: payload.type,
        district: payload.district?.trim() || null,
        city: payload.city?.trim() || null,
        state: payload.state?.trim() || null,
        country: payload.country?.trim() || null,
      })
      .select()
      .single();

    if (error) throw error;

    // Invalidate and refresh cache so the new institute is instantly selectable
    const existing = await this.fetchInstitutes(false);
    secureStorage.setCachedItemWithTTL(CACHE_KEY_INSTITUTES, [data, ...existing]);
    return data;
  }
};
```
